aidev: a control plane for delegating work to a coding agent

This guide is for someone who is new to the project. It assumes you know how to use a terminal. It assumes nothing else. Every new word is defined when it first appears.

What aidev is

aidev is a program you run on your own computer. It takes a unit of programming work, hands it to a coding agent, and then checks the result itself.

An agent is a program that writes code for you. In this project the agent is usually OpenCode, which is an existing open-source coding tool. A planner is whoever decides what should be built. The planner can be you at a terminal, or it can be Claude Code, which is a separate coding assistant that talks to aidev through a protocol called MCP. MCP stands for Model Context Protocol. It is just a way for two programs to call each other over a local connection.

Here is the short version of what aidev does with one piece of work:

aidev task create --title "Add a Greet function" --verify 'go test ./...'
aidev task run TASK-000001

The first command records the work. The second command runs it. Running means three steps: aidev isolates the work, the agent writes code, and then aidev runs the checks itself. The checks are called verification.

A task is one unit of delegated work. It has a title, an instruction for the agent, and a list of verification commands. A project is a git repository that aidev is allowed to run tasks against. git is a version control tool: it tracks every change to a set of files. A worktree is a second checkout of the same repository in a different directory, so two sets of files can exist side by side without interfering with each other.

All state lives in PostgreSQL, which is a database program. A database is a program that stores structured records durably on disk. aidev stores the task, every execution of it, the captured output, the resulting code change, the verification results, and a full history there. If aidev is killed halfway through, the records are still on disk.

Why aidev exists, and the one rule

An agent that reports its own success is not a source of truth. An agent can say "all done, tests pass" and be wrong. It can be wrong by mistake. The summary it writes and the code it writes are produced independently, and one run in this project's history produced correct code with an incoherent summary. The reverse also happens: an agent can report success while changing nothing at all.

The one rule: only verification can move a task to SUCCEEDED. aidev runs the task's own verification commands itself, in the task's worktree, and decides the outcome from their exit codes. An exit code is a number a command returns when it finishes: zero means success, anything else means failure. The agent saying the work is done changes nothing. There is no path from "the agent finished" to SUCCEEDED. The only path to SUCCEEDED passes through verification.

Let us say that again in different words, because everything else in this guide depends on it. When the agent finishes, the task is not done. It moves to a state called VERIFYING. Then aidev runs each verification command, one by one. If every command exits with zero, the task becomes SUCCEEDED. If any command fails, the task becomes FAILED, no matter what the agent claimed. The agent's claim is recorded word for word, because it helps with diagnosis, but it is never evidence.

Three more consequences follow from the same idea:

  • A task with no verification command is rejected when you create it. aidev will not accept work whose outcome it could not establish.
  • The agent writes only inside a dedicated git worktree. OpenCode was measured writing files with no permission prompt, so the worktree is the only containment boundary. Your own working files are never in reach of the agent.
  • History is append-only. The record of what happened is never rewritten. A mistake in the record is corrected by appending a new entry, not by editing the old one.

You can see the rule enforced in a test. The integration suite contains a test where the agent reports success without touching a single file, and the task ends FAILED with the claim stored next to the verification result that contradicts it.

Architecture: who does what

There are five pieces. Each one has exactly one job.

Claude Code or CLI (planner: decides WHAT to build)
        |
        |  MCP over stdio, or terminal commands
        v
   aidev (orchestration: isolates, bounds, verifies, records)
        |
        +---> OpenCode in a git worktree (agent: writes code, nothing else)
        |               |
        |               v
        +---> verification (aidev runs the task commands itself)
        |
        v
   PostgreSQL (state and event history)
ComponentWhat it isWhat it is responsible for
Planner (Claude Code or CLI)Either you typing commands at a terminal (a CLI is a command line interface), or Claude Code, a coding assistant that calls aidev through MCP.Deciding what to build. It never runs the agent directly and never judges success.
aidevThe program in this repository, written in Go, which is a compiled programming language.Orchestration: creating the worktree, starting the agent with a timeout, collecting the code change from git, running verification, and writing every record.
OpenCode in a worktreeThe coding agent, running with its working directory set to one isolated worktree.Writing code. It cannot reach your working files, it cannot decide the outcome, and its output is captured with a size limit.
VerificationThe task's own check commands, executed by aidev after the agent finishes.The decision. Only these exit codes can move a task to SUCCEEDED.
PostgreSQLA relational database that holds aidev's authoritative state.Remembering everything: tasks, attempts, output, diffs, verification results, and the append-only event history.

What aidev deliberately does not contain: no scheduler, no web dashboard, no authentication system, no automatic merge of branches. A successful task leaves a commit on its own branch, and a person decides what happens to that branch. Those are explicit non-goals, and the architecture document lists the extension points where each could plug in later.

The code is organized so each piece maps to a directory under internal/. The lifecycle lives in internal/worker. The agent boundary lives in internal/agent, so Claude Code never learns the OpenCode command line. Every external process goes through internal/procexec, which gives each one a deadline, cancellation, and bounded output. Configuration is read only by internal/config. Logs are written only by internal/logging, always to stderr.

The task lifecycle

A task moves through states. A state is the task's current situation, stored as a short word like RUNNING. A transition is one allowed move from one state to another. Not every move is allowed. The full list of allowed moves lives in internal/task/status.go, and tests assert its two most important properties.

PENDING --> READY --> RUNNING --> VERIFYING --> SUCCEEDED
   |            |             |               |
   |            |             +---------------+--> FAILED
   |            |
   +------------+--> WAITING_APPROVAL --+
                        |
   any non-terminal state --> CANCELLED

Reading the diagram from left to right:

  • PENDING means the task exists but is not yet eligible to run. In the current version nothing blocks a task, so it becomes ready as soon as a run is requested. The state exists so a future dependency feature has somewhere to hold a waiting task.
  • READY means the task is eligible to be picked up.
  • RUNNING means an agent is executing inside the task's worktree.
  • VERIFYING means the agent finished and aidev is now running the verification commands itself.
  • SUCCEEDED means verification passed. It is reachable only from VERIFYING. This is the one rule, drawn as a diagram: there is no arrow from RUNNING to SUCCEEDED.
  • FAILED means the attempt failed: the agent errored, timed out, or verification did not pass.
  • CANCELLED means a human or a shutdown stopped the task. Every non-terminal state can reach it, so no task can become unstoppable.
  • WAITING_APPROVAL means the task was created with a policy gate and will not execute until a human approves it. Approval granted moves it to READY. Approval denied moves it to FAILED.

There is deliberately no arrow from FAILED back to READY. A future retry feature would add that arrow. Attempts are already numbered and appended, so retry will be a matter of adding a row, but the edge does not exist yet, and adding it will be a deliberate change with a test to update.

One execution of a task is called an attempt. Attempts are numbered starting at 1 and are never overwritten. The worktree directory and the branch name both include the attempt number, so a second attempt can never collide with the first. A task that has never run has no attempt. A task that ran once has attempt 1.

Every state change is recorded as an event in the same database transaction as the change itself. An event is one immutable record of something that happened, with a sequence number, a type like task.started, and a small JSON payload. History therefore cannot disagree with state. You can read the history with:

aidev task events TASK-000001
aidev task result TASK-000001 --logs

The first command shows what happened, in order. The second shows the outcome, with the agent transcript and full verification output when you pass --logs. The debugging page explains both in detail.

Vocabulary

These eight words appear everywhere in aidev. Each one has a precise meaning here, which may be narrower than its everyday meaning.

WordWhat it means in aidev
taskOne unit of delegated work. It has a human-readable reference like TASK-000001, a title, an instruction for the agent, and at least one verification command. Tasks move through the lifecycle states above.
attemptOne execution of a task, numbered from 1. A task that runs once has one attempt. Attempts are appended, never overwritten, so the history of a task is the list of its attempts.
worktreeAn isolated git checkout where one attempt runs. The agent's working directory is set to the worktree, and the worktree path must resolve inside the configured workspace root. On success the work is committed to the task branch and the worktree is removed. On failure it is kept for inspection and marked RETAINED.
verificationThe task's own check commands, run by aidev itself after the agent finishes. Verification is the only thing that can move a task to SUCCEEDED. A task without at least one verification command cannot be created.
agentThe program that writes the code, usually OpenCode. The agent works inside the worktree and nothing else. Its report of what it did is recorded verbatim and never trusted.
eventOne immutable record in the task's history, for example task.created or task.verification_completed. Events have a total order given by sequence numbers. The log is append-only: corrections are new events, never edits.
projectA git repository aidev may run tasks against, registered by its absolute path. Creating a task for an unknown repository registers it automatically.
approvalA human decision gating a task. A task created with --requires-approval waits in WAITING_APPROVAL until a person grants or denies it with aidev task approve. A planner must never approve its own task.

If you remember only three of these, remember task, verification, and worktree. The task is the work. The worktree is where the agent does it. Verification is how aidev decides whether it worked.
