Debugging: how to find out what happened

Debugging means finding out what happened when something did not work as expected. aidev gives you four places to look: logs, the event history, the task result, and the retained worktree. This page explains each one, in the order to try them.

The one rule still applies while debugging: only verification can move a task to SUCCEEDED. When a task fails, the verification output is the verdict. The agent transcript is context. Do not read the agent's summary first and work backwards. Read the verification result first, then use the agent transcript to understand how it got there.

Where to look first

Start with the symptom. Match it to a starting point:

Logs: where they go and why they are on stderr

A log is a line of diagnostic text a program emits while it runs. Every program has two output streams: stdout (standard output) and stderr (standard error). By convention, stdout carries the program's actual answer and stderr carries diagnostics about how it got there.

aidev follows that convention strictly. Human-readable command output goes to stdout. All logging goes to stderr. There is one reason, and it is load-bearing rather than stylistic: when aidev runs as an MCP server, stdout carries the JSON-RPC protocol that Claude Code speaks. JSON-RPC is a format for one program to call functions on another over a pipe. One stray log line on stdout would corrupt that protocol stream. So the logging package has no stdout option at all. Removing the possibility is more reliable than remembering the rule.

This separation is also what makes JSON output composable. Because logs never touch stdout, this works:

aidev task get TASK-000001 --json | jq .status
# stdout carries JSON, so piping it to jq works;
# diagnostics stay visible on stderr, on your terminal

What success looks like: the status printed by jq, plus any log lines shown separately on your terminal. If jq complains about invalid input, something wrote non-JSON to stdout, which should never happen. Report it.

Log lines are structured. Each one carries fields you can use to follow one task through them:

Temporarily turn up logging by editing log_level to debug in your conf.json, then filter stderr into a file:

aidev task run TASK-000001 2> aidev.log
grep 'TASK-000001' aidev.log | head -20

The 2> part redirects stderr into a file. That is needed because logs go to stderr, not stdout. The fields to look for are task_id, attempt_id, and worktree_path. They are attached to a logger carried in the program's context, so deep code paths inherit them without passing a logger through every function. To follow one task, filter by its reference or id. To follow one execution, filter by the attempt id.

log_level controls how much is emitted. The allowed values are debug, info, warn, and error. The default is info. Set log_level to debug in conf.json when you need the full picture, for example when a task fails in a way the result does not explain. An unknown value fails at startup with a message naming the allowed values. aidev never logs secrets: connection strings are redacted before they are printed or logged, and the environment handed to a subprocess is never recorded.

If raising the log level does not explain a timing problem, turn on tracing instead, as described in the tracing section. Logs tell you what happened. Traces tell you how long each part took.

Events: reading the history, including while a task runs

The event history is the task's diary. Every state change and every major step appends an event in the same database transaction as the change, so history cannot disagree with state. Events have sequence numbers (seq) that give a total order independent of clock resolution: two events written in the same millisecond are still strictly ordered, which timestamps alone cannot guarantee.

Read the history with aidev task events:

aidev task events TASK-000001
# want, for a finished task, something like:
#   1       10:02:11.041  task.created
#   2       10:02:11.058  task.ready
#   3       10:02:12.004  task.started
#   4       10:02:12.031  task.worktree_created
#   5       10:02:12.040  task.worker_started
#   6       10:12:03.112  task.worker_completed
#   7       10:12:03.120  task.verification_started
#   8       10:12:03.205  task.verification_step_completed
#   9       10:12:03.208  task.verification_completed
#   10      10:12:03.220  task.succeeded

Each row shows the sequence number, the time in UTC, and the event type. The full vocabulary of event types is on the reference page. The important ones for diagnosis are task.created, task.ready, task.started, task.worktree_created, task.worker_started, task.worker_completed, task.verification_started, task.verification_step_completed, task.verification_completed, and the terminal trio task.succeeded, task.failed, task.cancelled.

Three flags change what you see:

aidev task events TASK-000001 --payload
# include each event's JSON payload, for example the verification exit codes

aidev task events TASK-000001 --after 5
# only events after sequence number 5; readers page with seq > last_seen

aidev task events TASK-000001 --json | jq .
# machine-readable output, same information as JSON

What success looks like: the events listed in order, with payloads shown when you ask for them. If the command says there are no events, the task reference is probably wrong, or the task was created but nothing has happened yet. Check the reference with aidev task list.

Watching a task while it runs means running the same command repeatedly from another terminal. A run takes minutes, and most of that is the agent, so the history tells you which stage it is in. If the last event is task.worker_started and several minutes have passed, the agent is still working. That is normal. If the last event is task.verification_started, aidev is running the checks itself and the end is near. For scripted polling, record the highest seq you have seen and pass it back as --after next time, so each call returns only what is new.

watch -n 10 'aidev task events TASK-000001 | tail -5'
# re-runs the command every 10 seconds; Ctrl-C stops watching
# if watch is not installed, just re-run aidev task events by hand

Task result: reading the outcome, including with full output

The result is the verdict plus the evidence. Read it with aidev task result:

aidev task result TASK-000001
# the outcome of the latest attempt: status, failure kind, timing,
# per-step verification results, and where the work is

aidev task result TASK-000001 --logs
# everything above, plus the agent transcript, the diff, and full output

aidev task result TASK-000001 --json | jq .verification
# just the verification section, as JSON

What each part means. The task section gives the status, for example SUCCEEDED or FAILED. The attempt section gives the attempt number, its status, the failure kind when it failed (such as VERIFICATION or TIMEOUT), and timing. The worker section describes what the agent did: its argv, its exit code, how many files changed, and its summary. The summary is the agent's claim about its own work, recorded verbatim. It is useful for diagnosis and it never decides anything. The verification section lists one entry per step with the command, the status, and the exit code. This is the evidence. The worktree section gives the path, the branch, and whether it was removed or RETAINED.

A failing step's output is included even without --logs, trimmed to the last 2000 bytes, because it is the first thing anyone needs. A passing step's output is not, to keep the display short. With --logs you get everything: the agent's stdout and stderr streams, the diff aidev collected from git, and the full verification output. Output beyond the per-stream capture limit is dropped and flagged as truncated, so a runaway agent cannot exhaust memory or the database.

If the task has never run, there is no attempt section. That is not an error. It means exactly what it says: the task was created and nothing has executed yet. Run it with aidev task run TASK-000001.

A worked reading of a failure. Suppose the result says FAILED with failure kind VERIFICATION, and the verification section shows go test ./... at exit 1 with output naming a missing function. The diagnosis is: the agent did not write the function, or wrote it with the wrong name. The fix is a better instruction, not a different command. Now check the worker summary: if it says "Done, all tests pass", you have the classic case the integration suite tests for, an agent claiming success while changing nothing. The claim is on record beside the contradiction. Trust the exit code.

Worktrees: finding and inspecting a retained failed task

A failed or cancelled task keeps its worktree on disk, untouched and uncommitted. The status RETAINED means exactly that: kept for inspection. There is deliberately no setting that discards failed work. The cleanup policy has two values only: on-success, which commits the work and removes the worktree, and never, which keeps every worktree. Neither discards failed work. As a backstop, plain git worktree remove refuses to delete a worktree holding uncommitted work, and aidev never passes --force automatically.

List what is being kept:

aidev worktree list
# each worktree with its task, its status, its size,
# and a flag when the directory is missing from disk

aidev worktree list --all
# also include worktrees aidev has already removed

aidev worktree list --json | jq .
# machine-readable form of the same list

What success looks like: one line per worktree, for example TASK-000002 FAILED attempt 1 RETAINED /path/to/worktrees/TASK-000002-a1, plus a total size at the end. A line flagged as missing from disk means something outside aidev deleted the directory. aidev tells you rather than showing a path that does not exist.

The status column has three possible values, and each one answers "where is the work?":

StatusWhat it meansWhere the work is
ACTIVEThe worktree exists and an attempt is using it. This is what you see while a task is running.In the worktree directory, still changing. Do not edit it by hand.
REMOVEDaidev deleted the directory after a clean success. Plain aidev worktree list hides these rows; --all shows them.Committed on the task's branch, for example aidev/TASK-000001. Nothing was lost: only the directory is gone.
RETAINEDaidev kept the directory because the attempt failed or was cancelled. It is never deleted implicitly.In the worktree directory, uncommitted, exactly as the agent left it.

Inspect a retained worktree directly. It is an ordinary directory with an ordinary git checkout in it. Change into it, look at the files, run the failing command by hand:

cd /home/you/.local/share/aidev/worktrees/TASK-000002-a1
git status --porcelain
git diff
go test ./...
# run the failing check yourself, in the worktree, to see the same failure

The path above is an example. Use the real path from aidev worktree list. Your workspace root may differ; aidev config shows it. Do not edit files in the retained worktree expecting the task to pick them up. The attempt is over. The worktree is evidence, not a second chance. If the partial work is worth keeping, copy the files out or commit them on the task branch yourself.

When you are done, reclaim the disk:

aidev worktree remove TASK-000002
# refused if the work is uncommitted, which protects a failed attempt's output

aidev worktree remove TASK-000002 --force
# discard the work permanently; the task's branch is left alone either way

Passing --force discards uncommitted work permanently and records the forced removal in the task's history as your decision. If the task is still RUNNING or VERIFYING, removal is refused: cancel it first. If the directory is already gone from disk, aidev reconciles the record rather than refusing, and prunes git's administrative entry.

Tracing: turning it on and viewing it

Tracing records how long each part of a run took, as a tree of spans. A span is one timed operation, like creating the worktree or running the agent. Tracing answers "where did the time go" in a way logs cannot. aidev exports traces in a standard format called OTLP, which keeps no vendor dependency: any backend that accepts OTLP works.

Tracing is off unless you configure an endpoint in conf.json. When it is off, instrumented code uses a no-op tracer, so there is no overhead and no network connection. To turn it on, point aidev at a backend by setting tracing.endpoint. The simplest backend for local use is Jaeger, which runs as one container with its UI on port 16686:

make jaeger-up
# then in conf.json, set tracing.endpoint to the local Jaeger:
#   "tracing": { "endpoint": "http://localhost:4318", ... }
# (make jaeger-env prints that URL)
export AIDEV_CONFIG="$PWD/conf/conf.json"
aidev task run TASK-000001

What success looks like: the run proceeds normally, and afterwards the Jaeger UI at http://localhost:16686 shows one trace for the run. Tracing reads its settings from conf.json, not from the shell: exporting an endpoint address on its own changes nothing, so the address has to be written into the tracing section of the file that AIDEV_CONFIG names. Confirm what aidev resolved with aidev config:

aidev config | grep -i tracing
# want: the endpoint you set, not "(none)"

A real run looks like this, with the agent dominating:

aidev.task.run            10.97s
  aidev.worktree.create    0.02s
  aidev.agent.run         10.86s   usage {input: 9580, output: 457}
  aidev.verification       0.08s
    aidev.verification.step   0s   go test ./... -> exit 0

That shape is typical: aidev's own work is a fraction of a second and the agent is everything else. If a run is slow, the trace shows it is the model, and the remedy is a faster model rather than tuning aidev.

The tracing keys, all optional, with their meaning. Each lives under the tracing object in conf.json; run aidev config to see what aidev resolved:

"tracing": {
  "endpoint": "https://example.com/otel",
  "traces_endpoint": "",
  "headers": { "Authorization": "Bearer secret" },
  "service_name": "aidev",
  "sample_ratio": 1
}

tracing.endpoint is the base OTLP HTTP URL; traces post to <base>/v1/traces. tracing.traces_endpoint is the full URL, used as given, and takes precedence when set. tracing.headers is an object of extra OTLP headers, such as an authorization header. tracing.service_name is the service name shown in the backend (default aidev). tracing.sample_ratio is a number from 0 to 1; 1 keeps everything. Tracing is off while both endpoints are empty.

Two traps are recorded here because both are easy to repeat. First, aidev deliberately does not pass its OTLP configuration to the agent subprocess: OpenCode is itself instrumented, and one run otherwise filed over a thousand spans of its own internals into the backend under aidev's name. Second, if you use self-hosted Langfuse, note version 4 removed GET /api/public/traces: use GET /api/public/v2/observations, and check the HTTP status code rather than reading an empty data field out of an error body.

Recovery: a task left RUNNING by a crash

If aidev is killed mid-run, by kill -9, a closed laptop, or a stopped container, the task is left in RUNNING with an open attempt and a worktree on disk. Nothing will pick it up again. A running task is not runnable, and aidev cannot know whether another process is still working on it. aidev deliberately does not expire a stale RUNNING task on its own: declaring a task dead while another process is still driving it would be worse than asking you to cancel it deliberately.

The way back is to cancel it. First find the stuck tasks, then cancel with a reason:

aidev task list --status RUNNING,VERIFYING
# find every task that was executing when aidev died

aidev task cancel TASK-000001 --reason "aidev was killed mid-run"
# moves it to CANCELLED, closes the open attempt, retains the worktree

What success looks like: the cancel command reports the task is CANCELLED, and aidev worktree list shows the worktree as RETAINED. The partial work survives and the task's history stays coherent, with the cancellation appended as a new event. Cancelling a task that already finished is an error naming that fact. Cancelling records the reason you gave in the task's history, so write one that your future self will understand.

After cancelling, inspect the retained worktree as described in the worktrees section, and remove it with aidev worktree remove once you are done. Create a new task, or re-run from the corrected state, rather than trying to resume the cancelled attempt. There is no resume in the current version: attempts are append-only and a cancelled attempt stays cancelled.

If none of these match, gather the three artifacts in this order and read them together: aidev task result TASK-000001 --logs, aidev task events TASK-000001 --payload, and the retained worktree from aidev worktree list. Between the verdict, the history, and the files, the cause is always in one of the three.
