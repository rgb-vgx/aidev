Getting started: from nothing to a finished task

This page takes you from an empty machine to a finished task. Follow it in order. Each step shows the full command, what success looks like, and what to do when it fails.

Keep the one rule in view: aidev runs the agent in an isolated git worktree, then runs the task's own verification commands itself, and only those commands can move a task to SUCCEEDED. The agent saying the work is done changes nothing. Everything you do below is preparation for that moment of verification.

Prerequisites: what you need, and how to check each one

A prerequisite is something that must already be installed before you begin. Here each one comes with a check command. Run the check. If the check fails, fix that item before moving on. Do not skip checks: almost every confusing failure later is really a missing prerequisite.

You needWhyHow to checkIf it fails
Go, version 1.25 or neweraidev is written in Go, and the MCP library requires a recent Go.go versionInstall Go from your system package manager or the Go website. With Go 1.24 the toolchain downloads a newer one automatically, but that needs network access.
git, version 2.23 or newerEvery task runs in a git worktree, which is a git feature.git --versionInstall git with your package manager, then run the check again.
Docker with ComposePostgreSQL runs in a container for local development.docker compose versionInstall Docker Desktop or the Docker engine plus the compose plugin, then make sure the Docker service is running.
OpenCode, version 1.18 or newerOpenCode is the agent that writes the code. You need it to run real tasks.opencode --versionInstall OpenCode and make sure the opencode program is on your PATH, or set agent.opencode.command to its location in conf.json (see configuration). No API key is needed for the public opencode/* models.

Run all four checks now, in full:

go version
# want: go1.25 or newer, for example: go version go1.26.8 linux/amd64

git --version
# want: git version 2.43.0 or similar (anything 2.23 or newer)

docker compose version
# want: Docker Compose version v5.5.1 or similar

opencode --version
# want: 1.18.30 or similar (anything 1.18 or newer)

A note on words: PATH is the list of directories your shell searches when you type a program name. If a program is "on your PATH", you can run it by name from anywhere. HOME is your home directory. A container is a lightweight isolated process managed by Docker; here it just means "PostgreSQL runs inside Docker so you do not have to install it".

Install: one command

Install aidev with one command:

curl -fsSL https://raw.githubusercontent.com/rgb-vgx/aidev/main/install.sh | sh

It downloads the release for your system (Linux or macOS, amd64 or arm64), checks the download against the release's SHA256SUMS file (a list of fingerprints: a download that does not match is refused, so a damaged or altered file is never installed), and puts aidev into ~/.local/bin. It does not need Go.

What success looks like: it prints "Installed aidev v0.1.0 to ..." and the next steps. Check with:

aidev version
# want: aidev v0.1.0 or similar

Being "on the PATH" means this: when you type a program name, your shell searches a list of directories called the PATH until it finds a matching program. The installer puts aidev into ~/.local/bin, which is one of those directories on many machines. If it is not on the PATH yet, the installer prints an export PATH line to add to ~/.bashrc or ~/.zshrc, so typing aidev ... works from any directory, in any terminal you open, instead of only from one folder.

To install a specific version:

curl -fsSL https://raw.githubusercontent.com/rgb-vgx/aidev/main/install.sh | AIDEV_VERSION=v0.1.0 sh

To install somewhere else:

curl -fsSL https://raw.githubusercontent.com/rgb-vgx/aidev/main/install.sh | AIDEV_INSTALL_DIR="$HOME/bin" sh

From source, for working on aidev

If you want to change aidev itself, build it from source instead.

git clone https://github.com/rgb-vgx/aidev.git
cd aidev
make build
# produces bin/aidev
./bin/aidev version
# want: aidev <version>, for example: aidev dev

What success looks like: the build finishes with no error, and bin/aidev exists. If make build fails, read the error, fix the named problem, and run make build again. It is safe to repeat.

Put aidev on your PATH so every terminal finds it:

make install
# runs: go install ./cmd/aidev

This guide uses aidev from here on. If you did not install it, type ./bin/aidev wherever you see aidev.

Database and configuration: one command, aidev setup

PostgreSQL is the database where aidev keeps everything. A migration is a versioned SQL file that creates or changes the database tables. Applying migrations means running those files in order so the database schema matches what the program expects. Migrations are embedded in the aidev program itself, so there is no separate migration tool to install.

The recommended way is one command:

aidev setup

What it does: it starts PostgreSQL in Docker in a container named aidev-postgres, listening only on this computer at 127.0.0.1:5434. It writes ~/.config/aidev/conf.json with database.url, a private file that is never overwritten if it already exists. It applies the migrations. Then it prints the export line and the Claude Code settings line to add.

It is safe to run again, for example after a reboot: it starts the container if it stopped and leaves your configuration alone.

What success looks like: it ends with aidev is set up. and a list of next steps.

If your company pulls Docker images from its own registry, tell setup which image to use:

aidev setup --postgres-image registry.example.com/library/postgres:16-alpine

If you already have PostgreSQL, point setup at it instead. Quote the URL. No Docker is needed, but the database must exist:

aidev setup --database-url 'postgres://user:password@host:5432/aidev'

If port 5434 is taken on your machine, pick another port:

aidev setup --postgres-port 5440

Next, point aidev at the file setup wrote, as described in the configuration section below, and check everything:

export AIDEV_CONFIG="$HOME/.config/aidev/conf.json"
# put that export line in your shell profile (~/.bashrc, ~/.zshrc, or equivalent)
aidev doctor

What success looks like: every line of aidev doctor should read ok, and each failure says how to fix it.

By hand, from the repository

If you work on aidev itself, you can do the same steps by hand from the repository instead of running aidev setup.

Start PostgreSQL:

make db-up
# starts PostgreSQL and waits until it is healthy

What success looks like: the command waits a few seconds and reports a healthy container. What the command does: it starts a PostgreSQL container that listens on your machine at 127.0.0.1:5434. That address means "this computer, port 5434". The port is 5434 rather than the usual 5432 because 5432 and 5433 were already taken on the machine where aidev was developed. If 5434 is taken on your machine too, override it:

AIDEV_DB_PORT=5440 make db-up

If make db-up fails, the usual causes are: Docker is not running (start it and try again), or the port is already in use (pick another port as shown above). The error names the cause. Fix it and repeat the command. It is safe to repeat.

Next, configure the connection and apply the schema. A connection string is a single line of text that tells a program how to reach a database: who to log in as, where, and with what options. You write it once into your conf.json under the key database.url, as described in the configuration section below:

cp conf/conf.example.json conf/conf.json
# then edit database.url in conf/conf.json if you changed the port
export AIDEV_CONFIG="$PWD/conf/conf.json"
# put that export line in your shell profile (~/.bashrc, ~/.zshrc, or equivalent)
aidev migrate
# want: "database is up to date (N migrations)" or a list of "applied ..." lines

Why each line matters. The first copies the example settings into conf/conf.json. Edit database.url if you used a different port. The second tells aidev which file is its conf.json: AIDEV_CONFIG must hold the file's absolute path, and it is the only environment variable aidev reads for configuration. The last applies pending migrations. aidev migrate is idempotent, which means running it twice is harmless: the second run finds nothing to do and says the database is up to date.

If aidev migrate says the configuration is invalid, it names the setting. If it cannot connect, check that make db-up is still running and that the port in database.url matches the port the database actually listens on. If you edited a migration file that was already applied, the migrator refuses to start and tells you: never edit an applied migration; add a new one instead.

Configuration: the conf.json file that matters

aidev reads its configuration from one JSON file: the conf.json that AIDEV_CONFIG names. AIDEV_CONFIG must hold the file's absolute path, and it is the only environment variable aidev reads for configuration. Everything lives in that file, and aidev validates it at startup and reports every problem at once, instead of failing halfway through a task.

Create the file once. Copy the example and point aidev at it:

cp conf/conf.example.json conf/conf.json
# then edit it: database.url, workspace_root, and anything else you need
export AIDEV_CONFIG="$PWD/conf/conf.json"
# put that export line in your shell profile (~/.bashrc, ~/.zshrc, or equivalent)
aidev config
# prints the resolved settings and which file it used

aidev reads nothing but the file that AIDEV_CONFIG names, so the export must be present in every new terminal. Put that line in your shell profile and this is one-time setup. A missing export is an error: aidev config says AIDEV_CONFIG is not set. A file that cannot be read is a different error that names the path: read config file <path>: .... A file that exists and cannot be parsed, or holds an unknown key, is an error that names the problem, so a broken setting is never silently ignored.

The file is JSON, so a value is literal text. Edit database.url when you change the database port; nothing else in the environment can override the file, so what you read in conf.json is what aidev uses.

The keys you will reach for first:

KeyDefaultWhat it doesWhat happens if it is wrong
database.urlnone: requiredHow aidev reaches PostgreSQL.Every command that touches the database fails at startup with a message naming database.url. Nothing runs.
workspace_root~/.local/share/aidev/worktreesThe directory under which every task worktree is created. Every worktree must resolve inside it.Task runs fail because the isolation directory cannot be prepared. The error names the path.
tasks.timeout30mHow long one agent run may take before aidev stops it.Too short and slow models get killed mid-work. The default is generous on purpose: a first run against a new repository was measured taking over four minutes before producing output.
agent.opencode.modelopencode/muse-spark-1.3-contributor-freeWhich model OpenCode uses. Set it to an empty string to let OpenCode choose.An unknown model makes the agent fail, which fails the task. The public default needs no credentials.

The full list, with every default, is on the reference page. To see exactly what aidev resolved, with the database password redacted:

aidev config
aidev config --json

What success looks like: a table of settings with your values. The database password shows as redacted. aidev config prints which file it used, or says none was found. If aidev config reports an error, it lists every problem. Fix them all, then run it again. A misconfiguration fails here, at startup, rather than surfacing halfway through a task, which is the point of the command.

First task: a worked example on a throwaway repository

Now the real thing. You will make a small practice repository whose test fails until the work is done, then ask aidev to do the work. A throwaway repository is a scratch project you can delete afterwards. Using one keeps your first run away from real code.

Why this shape of example: a task needs a verification command that fails before the work and passes after it. That is what proves verification is doing the deciding. A failing test is the honest starting point.

Step 1. Make the throwaway repository. A module here just means a small Go project. These commands create a directory, start a git repository in it, and add a test that cannot pass yet because the function it tests does not exist.

mkdir -p /tmp/aidev-demo
cd /tmp/aidev-demo
git init -b main
go mod init demo
cat > greet_test.go <<EOF
package main

import "testing"

func TestGreet(t *testing.T) {
    if Greet("Ada") != "Hello, Ada" {
        t.Fatalf("Greet returned the wrong string")
    }
}
EOF
go test ./...
# want: FAIL, something like: undefined: Greet
# that failure is the point: the test fails until the work is done

If go test ./... passes here, something is off: you may already have a greet.go file in the directory. Remove it and run the test again. You want a failing test.

Step 2. Create the task. The --verify flag gives one verification command. Repeat it for more than one. At least one is required: a task aidev cannot check is a task aidev will not accept.

cd /tmp/aidev-demo
aidev task create \
  --title "Add a Greet function" \
  --description "Create greet.go with Greet(name string) string returning Hello plus name" \
  --verify 'go test ./...' \
  --verify 'go vet ./...'
# want: created TASK-000001  Add a Greet function
#           run it with: aidev task run TASK-000001

What the flags mean: --title is one short line stating what to do. --description is the full instruction the agent will read. Each --verify is one command aidev will run itself, without a shell, to decide the outcome. The reference you get back, like TASK-000001, is how you name the task from now on.

If creation fails with a message about verification, you forgot --verify. If it complains the path is not a git repository, check you are inside /tmp/aidev-demo and that git status works there.

Step 3. Run it:

aidev task run TASK-000001

How long this takes: minutes, not seconds. Most of the wait is the model thinking, not aidev. aidev's own share of a run, worktree plus diff plus verification plus every database write, was measured at about 0.2 seconds against agent times of 9 to 656 seconds. The default model is the fast and consistent one, but free-tier latency varies. If it takes ten minutes, that is the model, not a bug. While it runs, you can watch the event log from another terminal, as described on the debugging page.

If the command is interrupted with Ctrl-C, the task is cancelled and the worktree is kept. That is safe. See recovery for what to do next.

Reading the result

When the run finishes, it tells you the outcome. A success looks like this:

TASK-000001 succeeded: 2/2 verification steps passed, work committed on aidev/TASK-000001

agent (opencode)
  outcome       SUCCEEDED
  changed files 1
  took          10m56s

verification (run by aidev)
  PASSED    go test ./...
  PASSED    go vet ./...

Read it in two halves. The agent half says what the agent did and what it claimed. The verification half says what aidev established itself. Only the second half decides. aidev task run exits with status zero on success and non-zero when the task did not succeed, so aidev task run TASK-000001 && ./deploy.sh behaves the way a shell user expects: the second command runs only if the task succeeded.

A failure looks like this instead:

TASK-000002 FAILED (VERIFICATION): verification did not pass: 0/1 steps passed

agent (opencode)
  outcome       SUCCEEDED
  changed files 0
  says          Done! I implemented the function and all tests pass.

verification (run by aidev)
  FAILED    go test ./...  (exit 1)

the work was kept for inspection

Notice the agent half: it claims success. Notice the verification half: the check failed. The task is FAILED, because only verification decides. This is the one rule in action. The agent's words are recorded because they help diagnosis. They are never evidence.

Two commands show you more whenever you need it:

aidev task result TASK-000001
aidev task result TASK-000001 --logs

The first shows the outcome of the latest attempt: status, timing, per-step verification results, and where the work is. The second adds the agent transcript, the diff, and the full verification output. A failing step's output is included even without --logs, trimmed to the last 2000 bytes, because it is the first thing anyone needs.

Where the work ends up, and how to review the branch with git

On success, aidev commits the agent's work to the task's own branch and removes the worktree. The branch is named after the task reference, for example aidev/TASK-000001. Nothing is merged into your branch. Nothing is ever committed to your working branch. Your own checkout stays clean.

Review the result with ordinary git commands. git log lists commits. git diff shows what changed between two branches.

cd /tmp/aidev-demo
git log --oneline aidev/TASK-000001
git diff main..aidev/TASK-000001
go clean -testcache && go test ./...
# run the test yourself on your own checkout of the branch:
# it should pass, because verification already passed in the worktree

On failure, the worktree is kept exactly as the agent left it, under workspace_root, and recorded as RETAINED. That is deliberate: partial work is often the most useful thing about a failure. Find it with aidev worktree list, inspect it, and remove it only when you are done. The debugging page walks through that.

When you are finished with the demo, delete the throwaway directory. Then continue with the guide index, the debugging page for everything that can go wrong, and the reference page for the complete flag and variable lists.

cd /tmp
rm -rf /tmp/aidev-demo
aidev task list
# your demo task is still in PostgreSQL: the record outlives the directory

Coming back tomorrow: if you closed your terminal, there is nothing to set up again except the shell export. Make sure PostgreSQL is running with make db-up, then just run aidev. Your configuration is already in the conf.json that AIDEV_CONFIG names, the export in your shell profile puts it in every new terminal, and make install means the aidev command is still found. Check with aidev config if you want proof before running a task.

Connecting Claude Code: delegating from any repository

Everything so far used aidev from a terminal. aidev is built to be driven by Claude Code: Claude Code decides what to build and writes the task, aidev isolates it, runs the agent, and checks the result itself. The two talk over MCP (Model Context Protocol), a standard way for Claude Code to call tools that live in another program. You register aidev once, and it is available in every repository on the machine.

make install
# puts aidev in $(go env GOPATH)/bin, a path that does not move

claude mcp add --scope user -e AIDEV_CONFIG=/abs/path/conf.json aidev -- "$(go env GOPATH)/bin/aidev" mcp
# registers aidev for every project on this machine; use the absolute path
# of the same conf.json that aidev config reports

Use --scope user. Without it, Claude Code uses the local scope, which ties the registration to the directory you ran the command in. aidev then works in that one repository and does not exist in any other. There is no error message: the tools are simply missing. That is the mistake this paragraph is here to prevent.

No password or connection string goes on the registration except through the file it names. aidev reads the conf.json that AIDEV_CONFIG names, the same file the terminal commands use, so aidev config shows you exactly what the MCP server will see.

Check the registration from a directory that is not the aidev repository, because that is where a wrong scope shows up:

cd /tmp
claude mcp get aidev

What success looks like. The line that matters is the scope:

aidev:
  Scope: User config (available in all your projects)
  Status: ✔ Connected
  Type: stdio
  Command: /home/you/go/bin/aidev
  Args: mcp

If the scope line says anything other than User config, remove the registration with the command printed on the last line of that output, then run the claude mcp add --scope user command again. If the status is not Connected, aidev could not start: run aidev config in a terminal, which fails with the same reason the MCP server would.

Start a new Claude Code session after registering. A session that was already open does not pick up a server added later.

Using it in another repository needs nothing per repository. Open Claude Code in that repository, for example in VS Code, and ask in plain words, naming the check that proves the work: "Use aidev to add a farewell function to greet.py, verified by python3 -m pytest -q." Claude Code calls aidev_create_task and aidev_run_task, then reads aidev_get_task_result. The field that decides is succeeded, which is true only when aidev's own verification passed. The only requirements are that the repository is a git repository and that PostgreSQL is running (make db-up in the aidev directory).

One thing that surprises people in a real repository: the worktree is a clean checkout, so it contains only files tracked by git. Anything installed outside git is not there. go test works because Go's module cache is shared, but a Python or JavaScript project needs its test tool installed on the machine, or a verification step that installs it first. The reference page lists every tool and its inputs.
