Getting started: from nothing to a finished task

This page takes you from an empty machine to a finished task. Follow it in order. Each step shows the full command, what success looks like, and what to do when it fails.

Keep the one rule in view: aidev runs the agent in an isolated git worktree, then runs the task's own verification commands itself, and only those commands can move a task to SUCCEEDED. The agent saying the work is done changes nothing. Everything you do below is preparation for that moment of verification.

Prerequisites: what you need, and how to check each one

A prerequisite is something that must already be installed before you begin. Here each one comes with a check command. Run the check. If the check fails, fix that item before moving on. Do not skip checks: almost every confusing failure later is really a missing prerequisite.

You needWhyHow to checkIf it fails
Go, version 1.25 or neweraidev is written in Go, and the MCP library requires a recent Go.go versionInstall Go from your system package manager or the Go website. With Go 1.24 the toolchain downloads a newer one automatically, but that needs network access.
git, version 2.23 or newerEvery task runs in a git worktree, which is a git feature.git --versionInstall git with your package manager, then run the check again.
Docker with ComposePostgreSQL runs in a container for local development.docker compose versionInstall Docker Desktop or the Docker engine plus the compose plugin, then make sure the Docker service is running.
OpenCode, version 1.18 or newerOpenCode is the agent that writes the code. You need it to run real tasks.opencode --versionInstall OpenCode and make sure the opencode program is on your PATH, or set OPENCODE_COMMAND to its location. No API key is needed for the public opencode/* models.

Run all four checks now, in full:

go version
# want: go1.25 or newer, for example: go version go1.26.8 linux/amd64

git --version
# want: git version 2.43.0 or similar (anything 2.23 or newer)

docker compose version
# want: Docker Compose version v5.5.1 or similar

opencode --version
# want: 1.18.30 or similar (anything 1.18 or newer)

A note on words: PATH is the list of directories your shell searches when you type a program name. If a program is "on your PATH", you can run it by name from anywhere. HOME is your home directory. A container is a lightweight isolated process managed by Docker; here it just means "PostgreSQL runs inside Docker so you do not have to install it".

Install: building aidev

Building means turning the source code into a runnable program. Get the repository first, then build it.

git clone <this repository> aidev
cd aidev
make build
# produces bin/aidev

What success looks like: the last command finishes with no error, and bin/aidev exists. Check with:

ls bin/aidev
./bin/aidev version
# want: aidev <version>, for example: aidev dev

If make build fails, read the error. A missing Go installation says go: command not found. A network problem during the toolchain download says something about fetching the toolchain. Fix the named problem and run make build again. It is safe to repeat.

If you prefer the program on your PATH so you can type aidev from any directory:

make install
# runs: go install ./cmd/aidev

This guide uses aidev from here on. If you did not install it, type ./bin/aidev wherever you see aidev.

Database: starting PostgreSQL and applying migrations

PostgreSQL is the database where aidev keeps everything. A migration is a versioned SQL file that creates or changes the database tables. Applying migrations means running those files in order so the database schema matches what the program expects. Migrations are embedded in the aidev program itself, so there is no separate migration tool to install.

Start PostgreSQL:

make db-up
# starts PostgreSQL and waits until it is healthy

What success looks like: the command waits a few seconds and reports a healthy container. What the command does: it starts a PostgreSQL container that listens on your machine at 127.0.0.1:5434. That address means "this computer, port 5434". The port is 5434 rather than the usual 5432 because 5432 and 5433 were already taken on the machine where aidev was developed. If 5434 is taken on your machine too, override it:

AIDEV_DB_PORT=5440 make db-up

If make db-up fails, the usual causes are: Docker is not running (start it and try again), or the port is already in use (pick another port as shown above). The error names the cause. Fix it and repeat the command. It is safe to repeat.

Next, configure the connection and apply the schema. A connection string is a single line of text that tells a program how to reach a database: who to log in as, where, and with what options.

cp .env.example .env
export DATABASE_URL='postgres://aidev:aidev@127.0.0.1:5434/aidev?sslmode=disable'
aidev migrate
# want: "database is up to date (N migrations)" or a list of "applied ..." lines

Why each line matters. The first copies the example environment file. Edit .env if you changed the port. The second sets DATABASE_URL in your current shell. The third applies pending migrations. aidev migrate is idempotent, which means running it twice is harmless: the second run finds nothing to do and says the database is up to date.

If aidev migrate says the configuration is invalid, it names the variable. If it cannot connect, check that make db-up is still running and that the port in DATABASE_URL matches the port the database actually listens on. If you edited a migration file that was already applied, the migrator refuses to start and tells you: never edit an applied migration; add a new one instead.

Configuration: the environment variables that matter

aidev reads its configuration from environment variables. An environment variable is a named value attached to your shell session, like DATABASE_URL above. Only one part of aidev reads them, and it validates everything at startup and reports every problem at once, instead of failing halfway through a task.

VariableDefaultWhat it doesWhat happens if it is wrong
DATABASE_URLnone: requiredHow aidev reaches PostgreSQL.Every command that touches the database fails at startup with a message naming DATABASE_URL. Nothing runs.
WORKSPACE_ROOT$XDG_DATA_HOME/aidev/worktrees or ~/.local/share/aidev/worktreesThe directory under which every task worktree is created. Every worktree must resolve inside it.Task runs fail because the isolation directory cannot be prepared. The error names the path.
DEFAULT_TASK_TIMEOUT30mHow long one agent run may take before aidev stops it.Too short and slow models get killed mid-work. The default is generous on purpose: a first run against a new repository was measured taking over four minutes before producing output.
OPENCODE_MODELopencode/muse-spark-1.3-contributor-freeWhich model OpenCode uses. Set it to an empty string to let OpenCode choose.An unknown model makes the agent fail, which fails the task. The public default needs no credentials.
LOG_LEVELinfoHow much log detail aidev emits: debug, info, warn, or error.An unknown value fails startup. Too quiet and you lose diagnosis; too loud and the signal drowns.

The full list, with every default, is on the reference page. To see exactly what aidev resolved, with the database password redacted:

aidev config
aidev config --json

What success looks like: a table of settings with your values. The database password shows as redacted. If aidev config reports an error, it lists every problem. Fix them all, then run it again. A misconfiguration fails here, at startup, rather than surfacing halfway through a task, which is the point of the command.

First task: a worked example on a throwaway repository

Now the real thing. You will make a small practice repository whose test fails until the work is done, then ask aidev to do the work. A throwaway repository is a scratch project you can delete afterwards. Using one keeps your first run away from real code.

Why this shape of example: a task needs a verification command that fails before the work and passes after it. That is what proves verification is doing the deciding. A failing test is the honest starting point.

Step 1. Make the throwaway repository. A module here just means a small Go project. These commands create a directory, start a git repository in it, and add a test that cannot pass yet because the function it tests does not exist.

mkdir -p /tmp/aidev-demo
cd /tmp/aidev-demo
git init -b main
go mod init demo
cat > greet_test.go <<EOF
package main

import "testing"

func TestGreet(t *testing.T) {
    if Greet("Ada") != "Hello, Ada" {
        t.Fatalf("Greet returned the wrong string")
    }
}
EOF
go test ./...
# want: FAIL, something like: undefined: Greet
# that failure is the point: the test fails until the work is done

If go test ./... passes here, something is off: you may already have a greet.go file in the directory. Remove it and run the test again. You want a failing test.

Step 2. Create the task. The --verify flag gives one verification command. Repeat it for more than one. At least one is required: a task aidev cannot check is a task aidev will not accept.

cd /tmp/aidev-demo
aidev task create \
  --title "Add a Greet function" \
  --description "Create greet.go with Greet(name string) string returning Hello plus name" \
  --verify 'go test ./...' \
  --verify 'go vet ./...'
# want: created TASK-000001  Add a Greet function
#           run it with: aidev task run TASK-000001

What the flags mean: --title is one short line stating what to do. --description is the full instruction the agent will read. Each --verify is one command aidev will run itself, without a shell, to decide the outcome. The reference you get back, like TASK-000001, is how you name the task from now on.

If creation fails with a message about verification, you forgot --verify. If it complains the path is not a git repository, check you are inside /tmp/aidev-demo and that git status works there.

Step 3. Run it:

aidev task run TASK-000001

How long this takes: minutes, not seconds. Most of the wait is the model thinking, not aidev. aidev's own share of a run, worktree plus diff plus verification plus every database write, was measured at about 0.2 seconds against agent times of 9 to 656 seconds. The default model is the fast and consistent one, but free-tier latency varies. If it takes ten minutes, that is the model, not a bug. While it runs, you can watch the event log from another terminal, as described on the debugging page.

If the command is interrupted with Ctrl-C, the task is cancelled and the worktree is kept. That is safe. See recovery for what to do next.

Reading the result

When the run finishes, it tells you the outcome. A success looks like this:

TASK-000001 succeeded: 2/2 verification steps passed, work committed on aidev/TASK-000001

agent (opencode)
  outcome       SUCCEEDED
  changed files 1
  took          10m56s

verification (run by aidev)
  PASSED    go test ./...
  PASSED    go vet ./...

Read it in two halves. The agent half says what the agent did and what it claimed. The verification half says what aidev established itself. Only the second half decides. aidev task run exits with status zero on success and non-zero when the task did not succeed, so aidev task run TASK-000001 && ./deploy.sh behaves the way a shell user expects: the second command runs only if the task succeeded.

A failure looks like this instead:

TASK-000002 FAILED (VERIFICATION): verification did not pass: 0/1 steps passed

agent (opencode)
  outcome       SUCCEEDED
  changed files 0
  says          Done! I implemented the function and all tests pass.

verification (run by aidev)
  FAILED    go test ./...  (exit 1)

the work was kept for inspection

Notice the agent half: it claims success. Notice the verification half: the check failed. The task is FAILED, because only verification decides. This is the one rule in action. The agent's words are recorded because they help diagnosis. They are never evidence.

Two commands show you more whenever you need it:

aidev task result TASK-000001
aidev task result TASK-000001 --logs

The first shows the outcome of the latest attempt: status, timing, per-step verification results, and where the work is. The second adds the agent transcript, the diff, and the full verification output. A failing step's output is included even without --logs, trimmed to the last 2000 bytes, because it is the first thing anyone needs.

Where the work ends up, and how to review the branch with git

On success, aidev commits the agent's work to the task's own branch and removes the worktree. The branch is named after the task reference, for example aidev/TASK-000001. Nothing is merged into your branch. Nothing is ever committed to your working branch. Your own checkout stays clean.

Review the result with ordinary git commands. git log lists commits. git diff shows what changed between two branches.

cd /tmp/aidev-demo
git log --oneline aidev/TASK-000001
git diff main..aidev/TASK-000001
go clean -testcache && go test ./...
# run the test yourself on your own checkout of the branch:
# it should pass, because verification already passed in the worktree

On failure, the worktree is kept exactly as the agent left it, under WORKSPACE_ROOT, and recorded as RETAINED. That is deliberate: partial work is often the most useful thing about a failure. Find it with aidev worktree list, inspect it, and remove it only when you are done. The debugging page walks through that.

When you are finished with the demo, delete the throwaway directory. Then continue with the guide index, the debugging page for everything that can go wrong, and the reference page for the complete flag and variable lists.

cd /tmp
rm -rf /tmp/aidev-demo
aidev task list
# your demo task is still in PostgreSQL: the record outlives the directory
