Bắt đầu: từ con số không tới một task hoàn chỉnh

Trang này đưa bạn từ một máy trống trơn tới một task chạy xong. Hãy làm theo đúng thứ tự. Mỗi bước đều có lệnh đầy đủ, mô tả kết quả đúng trông ra sao, và cách xử lý khi gặp lỗi.

Nhớ quy tắc duy nhất: aidev chạy agent trong một worktree git tách biệt, rồi tự chạy các lệnh verification của task, và chỉ các lệnh đó mới được đưa task sang SUCCEEDED. Agent nói công việc đã xong cũng không thay đổi điều gì. Mọi thứ bạn làm dưới đây đều là chuẩn bị cho khoảnh khắc verification đó.

Điều kiện cần: những gì phải có, và cách kiểm tra từng thứ

Điều kiện cần là thứ phải cài sẵn trước khi bắt đầu. Mỗi thứ dưới đây đều kèm lệnh kiểm tra. Hãy chạy lệnh kiểm tra, nếu hỏng thì sửa xong rồi mới đi tiếp. Đừng bỏ qua bước kiểm tra: hầu hết lỗi khó hiểu về sau thực chất chỉ là thiếu một điều kiện cần.

Chạy cả bốn lệnh kiểm tra ngay bây giờ, đầy đủ:

go version

Giải thích vài từ: PATH là danh sách thư mục mà shell lục tìm mỗi khi bạn gõ tên một chương trình. Chương trình "nằm trên PATH" nghĩa là bạn gõ tên nó ở đâu cũng chạy. HOME là thư mục nhà của bạn. container là một tiến trình cách ly nhẹ do Docker quản lý; ở đây chỉ cần hiểu là "PostgreSQL chạy trong Docker nên bạn khỏi phải cài trực tiếp".

Cài đặt: biên dịch aidev

Biên dịch nghĩa là biến mã nguồn thành chương trình chạy được. Lấy kho mã về trước, rồi biên dịch.

git clone <this repository> aidev
cd aidev
make build
# produces bin/aidev

Dấu hiệu thành công: lệnh cuối kết thúc không lỗi, và tập tin bin/aidev tồn tại. Kiểm tra bằng:

ls bin/aidev
./bin/aidev version
# want: aidev <version>, for example: aidev dev

Nếu make build hỏng, hãy đọc thông báo lỗi. Thiếu Go thì nó báo go: command not found. Lỗi mạng khi tải toolchain thì báo gì đó về fetching toolchain. Sửa đúng lỗi được nêu rồi chạy lại make build. Chạy lại thoải mái, không sao cả.

Nếu muốn gõ aidev ở thư mục nào cũng được, tức là đưa chương trình lên PATH:

make install
# runs: go install ./cmd/aidev

Từ đây hướng dẫn sẽ viết aidev. Nếu bạn không cài theo cách đó thì chỗ nào thấy aidev hãy gõ ./bin/aidev.

Cơ sở dữ liệu: khởi động PostgreSQL và chạy migration

PostgreSQL là nơi aidev cất mọi thứ. Migration là tập tin SQL có đánh phiên bản, dùng để tạo hoặc sửa các bảng trong cơ sở dữ liệu. Chạy migration nghĩa là thực thi các tập tin đó theo thứ tự để cấu trúc cơ sở dữ liệu khớp với những gì chương trình mong đợi. Migration được nhúng sẵn trong chính chương trình aidev nên bạn không cần cài thêm công cụ migration nào.

Khởi động PostgreSQL:

make db-up
# starts PostgreSQL and waits until it is healthy

Dấu hiệu thành công: lệnh chờ vài giây rồi báo container đã khỏe. Lệnh này làm gì: nó khởi động một container PostgreSQL lắng nghe trên máy bạn ở 127.0.0.1:5434. Địa chỉ đó nghĩa là "chính máy này, cổng 5434". Cổng là 5434 chứ không phải 5432 như thường lệ, vì 5432 và 5433 đã bị chiếm trên máy phát triển aidev. Nếu 5434 trên máy bạn cũng bị chiếm thì đổi cổng:

AIDEV_DB_PORT=5440 make db-up

Nếu make db-up hỏng thì thường do hai nguyên nhân: Docker chưa chạy (bật Docker lên rồi thử lại), hoặc cổng đã có chương trình khác dùng (chọn cổng khác như trên). Thông báo lỗi sẽ nêu rõ nguyên nhân. Sửa rồi chạy lại lệnh, chạy lại thoải mái.

Tiếp theo, cấu hình kết nối rồi áp cấu trúc bảng. Chuỗi kết nối là một dòng chữ duy nhất cho chương trình biết cách tới cơ sở dữ liệu: đăng nhập tên gì, ở đâu, kèm tùy chọn gì.

cp .env.example .env
export DATABASE_URL='postgres://aidev:aidev@127.0.0.1:5434/aidev?sslmode=disable'
aidev migrate
# want: "database is up to date (N migrations)" or a list of "applied ..." lines

Vì sao mỗi dòng quan trọng. Dòng đầu sao chép tập tin môi trường mẫu. Nếu đổi cổng thì sửa .env cho khớp. Dòng thứ hai đặt DATABASE_URL cho shell hiện tại. Dòng thứ ba áp các migration còn thiếu. aidev migrate có tính lũy đẳng, tức là chạy hai lần cũng không sao: lần thứ hai chẳng còn gì để làm và nó báo cơ sở dữ liệu đã cập nhật.

Nếu aidev migrate báo cấu hình không hợp lệ thì nó sẽ nêu tên biến. Nếu không kết nối được thì kiểm tra xem make db-up còn chạy không, và cổng trong DATABASE_URL có khớp với cổng cơ sở dữ liệu đang nghe không. Nếu bạn sửa một tập tin migration đã áp rồi thì bộ migrator sẽ từ chối khởi động và nói rõ: đừng bao giờ sửa migration đã áp, hãy thêm migration mới.

Cấu hình: các biến môi trường quan trọng

aidev đọc cấu hình từ biến môi trường. Biến môi trường là một giá trị có tên gắn với phiên shell của bạn, như DATABASE_URL ở trên. Chỉ một bộ phận của aidev đọc chúng, và nó kiểm tra mọi thứ ngay khi khởi động rồi báo hết mọi lỗi một lúc, thay vì chạy nửa chừng mới đổ vỡ.

Danh sách đầy đủ kèm mọi giá trị mặc định nằm ở trang tra cứu. Muốn xem chính xác aidev đã nhận gì, với mật khẩu cơ sở dữ liệu đã che đi:

aidev config
aidev config --json

Dấu hiệu thành công: một bảng thiết lập với giá trị của bạn. Mật khẩu cơ sở dữ liệu hiện dạng đã che. Nếu aidev config báo lỗi thì nó liệt kê mọi vấn đề. Sửa hết rồi chạy lại. Cấu hình sai lộ mặt ở đây, ngay khi khởi động, chứ không đợi tới giữa task mới bung ra, đó chính là ý nghĩa của lệnh này.

Task đầu tiên: ví dụ làm thật trên kho mã dùng một lần

Giờ tới phần thật. Bạn sẽ tạo một kho mã thực hành nhỏ mà test của nó hỏng cho tới khi việc xong, rồi nhờ aidev làm. Kho mã dùng một lần là dự án nháp để xóa sau. Dùng nó để lần chạy đầu tiên tránh xa code thật.

Vì sao ví dụ có hình dạng này: task cần một lệnh verification hỏng trước khi làm và qua sau khi làm xong. Có vậy mới chứng minh được verification là bên quyết định. Một test đang hỏng là điểm xuất phát trung thực.

Bước 1. Tạo kho mã dùng một lần. Module ở đây chỉ là một dự án Go nhỏ. Các lệnh dưới tạo thư mục, khởi tạo kho git trong đó, rồi thêm một test chắc chắn hỏng vì hàm nó kiểm tra còn chưa tồn tại.

mkdir -p /tmp/aidev-demo
cd /tmp/aidev-demo
git init -b main
go mod init demo
cat > greet_test.go <<EOF
package main

import "testing"

func TestGreet(t *testing.T) {
    if Greet("Ada") != "Hello, Ada" {
        t.Fatalf("Greet returned the wrong string")
    }
}
EOF
go test ./...
# want: FAIL, something like: undefined: Greet
# that failure is the point: the test fails until the work is done

Nếu go test ./... ở đây lại qua thì có gì đó sai: có thể trong thư mục đã sẵn một tập tin greet.go. Xóa nó rồi chạy test lại. Bạn muốn một test đang hỏng.

Bước 2. Tạo task. Cờ --verify cho một lệnh verification. Muốn nhiều lệnh thì lặp lại cờ đó. Ít nhất một lệnh là bắt buộc: task mà aidev không kiểm được thì aidev không nhận.

cd /tmp/aidev-demo
aidev task create \
  --title "Add a Greet function" \
  --description "Create greet.go with Greet(name string) string returning Hello plus name" \
  --verify 'go test ./...' \
  --verify 'go vet ./...'
# want: created TASK-000001  Add a Greet function
#           run it with: aidev task run TASK-000001

Ý nghĩa các cờ: --title là một dòng ngắn nói cần làm gì. --description là hướng dẫn đầy đủ agent sẽ đọc. Mỗi --verify là một lệnh aidev tự chạy, không qua shell, để quyết định kết quả. Mã tham chiếu bạn nhận lại, kiểu TASK-000001, là cách gọi tên task từ nay về sau.

Nếu tạo thất bại với thông báo về verification thì bạn đã quên --verify. Nếu nó than đường dẫn không phải kho git thì kiểm tra xem bạn có đang ở trong /tmp/aidev-demo không và git status ở đó có chạy không.

Bước 3. Chạy nó:

aidev task run TASK-000001

Lệnh này mất bao lâu: tính bằng phút chứ không phải giây. Phần lớn thời gian chờ là model suy nghĩ, không phải aidev. Phần việc của riêng aidev trong một lần chạy, gồm tạo worktree, lấy diff, chạy verification và mọi lần ghi cơ sở dữ liệu, được đo chỉ khoảng 0,2 giây, trong khi agent tốn từ 9 tới 656 giây. Model mặc định là bản nhanh và ổn định, nhưng độ trễ của bản miễn phí thất thường. Nếu mất mười phút thì đó là do model, không phải lỗi. Trong lúc chạy, bạn có thể mở terminal khác xem nhật ký event như trang gỡ lỗi mô tả.

Nếu lệnh bị ngắt bằng Ctrl-C thì task bị hủy và worktree được giữ lại. Như vậy là an toàn. Xem phần khôi phục để biết bước tiếp theo.

Đọc kết quả

Khi chạy xong, lệnh sẽ báo kết quả. Thành công trông thế này:

TASK-000001 succeeded: 2/2 verification steps passed, work committed on aidev/TASK-000001

agent (opencode)
  outcome       SUCCEEDED
  changed files 1
  took          10m56s

verification (run by aidev)
  PASSED    go test ./...
  PASSED    go vet ./...

Đọc nó làm hai nửa. Nửa agent nói agent đã làm gì và nó nói gì. Nửa verification nói aidev tự xác minh được gì. Chỉ nửa thứ hai quyết định. aidev task run thoát với mã 0 khi thành công và mã khác 0 khi task không thành công, nên aidev task run TASK-000001 && ./deploy.sh đúng như người dùng shell mong đợi: lệnh thứ hai chỉ chạy khi task đã thành công.

Thất bại trông thế này:

TASK-000002 FAILED (VERIFICATION): verification did not pass: 0/1 steps passed

agent (opencode)
  outcome       SUCCEEDED
  changed files 0
  says          Done! I implemented the function and all tests pass.

verification (run by aidev)
  FAILED    go test ./...  (exit 1)

the work was kept for inspection

Để ý nửa agent: nó nói thành công. Để ý nửa verification: bước kiểm tra hỏng. Task là FAILED, vì chỉ verification quyết định. Đây là quy tắc duy nhất trong thực tế. Lời agent được ghi lại vì giúp chẩn đoán, chứ không bao giờ là bằng chứng.

Hai lệnh cho bạn xem thêm bất cứ khi nào cần:

aidev task result TASK-000001
aidev task result TASK-000001 --logs

Lệnh đầu cho kết quả của attempt mới nhất: trạng thái, thời gian, kết quả verification từng bước, và công việc đang ở đâu. Lệnh thứ hai thêm bản ghi của agent, diff và toàn bộ output verification. Output của bước hỏng luôn được kèm theo ngay cả khi không có --logs, cắt lấy 2000 byte cuối, vì đó là thứ ai cũng cần đầu tiên.

Công việc nằm ở đâu, và cách xem lại nhánh bằng git

Khi thành công, aidev commit phần việc của agent lên nhánh (branch) riêng của task rồi xóa worktree. Nhánh đặt tên theo mã task, ví dụ aidev/TASK-000001. Không có gì được merge vào nhánh của bạn. Không bao giờ có commit nào lên nhánh bạn đang làm. Bản checkout của bạn vẫn sạch.

Xem lại kết quả bằng lệnh git thường. git log liệt kê commit. git diff cho thấy hai nhánh khác nhau chỗ nào.

cd /tmp/aidev-demo
git log --oneline aidev/TASK-000001
git diff main..aidev/TASK-000001
go clean -testcache && go test ./...
# run the test yourself on your own checkout of the branch:
# it should pass, because verification already passed in the worktree

Khi thất bại, worktree được giữ nguyên như agent để lại, nằm dưới WORKSPACE_ROOT, và ghi nhận là RETAINED. Đó là chủ ý: công việc dở dang thường là thứ hữu ích nhất của một lần hỏng. Tìm nó bằng aidev worktree list, xem xét, và chỉ xóa khi đã xong. Trang gỡ lỗi hướng dẫn từng bước việc đó.

Làm xong demo thì xóa thư mục dùng một lần. Rồi đọc tiếp trang đầu hướng dẫn, trang gỡ lỗi cho mọi thứ có thể hỏng, và trang tra cứu cho danh sách đầy đủ cờ và biến.

cd /tmp
rm -rf /tmp/aidev-demo
aidev task list
# your demo task is still in PostgreSQL: the record outlives the directory
