Bắt đầu: từ con số không tới một task hoàn chỉnh

Trang này đưa bạn từ một máy trống trơn tới một task chạy xong. Hãy làm theo đúng thứ tự. Mỗi bước đều có lệnh đầy đủ, mô tả kết quả đúng trông ra sao, và cách xử lý khi gặp lỗi.

Nhớ quy tắc duy nhất: aidev chạy agent trong một worktree git tách biệt, rồi tự chạy các lệnh verification của task, và chỉ các lệnh đó mới được đưa task sang SUCCEEDED. Agent nói công việc đã xong cũng không thay đổi điều gì. Mọi thứ bạn làm dưới đây đều là chuẩn bị cho khoảnh khắc verification đó.

Điều kiện cần: những gì phải có, và cách kiểm tra từng thứ

Điều kiện cần là thứ phải cài sẵn trước khi bắt đầu. Mỗi thứ dưới đây đều kèm lệnh kiểm tra. Hãy chạy lệnh kiểm tra, nếu hỏng thì sửa xong rồi mới đi tiếp. Đừng bỏ qua bước kiểm tra: hầu hết lỗi khó hiểu về sau thực chất chỉ là thiếu một điều kiện cần.

Bạn cầnĐể làm gìKiểm tra thế nàoNếu hỏng thì sao
Go, bản 1.25 trở lênaidev viết bằng Go, và thư viện MCP đòi Go bản mới.go versionCài Go từ trình quản lý gói của hệ điều hành hoặc trang chủ Go. Với Go 1.24, toolchain sẽ tự tải bản mới hơn, nhưng việc đó cần mạng.

Chạy cả bốn lệnh kiểm tra ngay bây giờ, đầy đủ:

go version
# want: go1.25 or newer, for example: go version go1.26.8 linux/amd64

git --version
# want: git version 2.43.0 or similar (anything 2.23 or newer)

docker compose version
# want: Docker Compose version v5.5.1 or similar

opencode --version
# want: 1.18.30 or similar (anything 1.18 or newer)

Giải thích vài từ: PATH là danh sách thư mục mà shell lục tìm mỗi khi bạn gõ tên một chương trình. Chương trình "nằm trên PATH" nghĩa là bạn gõ tên nó ở đâu cũng chạy. HOME là thư mục nhà của bạn. container là một tiến trình cách ly nhẹ do Docker quản lý; ở đây chỉ cần hiểu là "PostgreSQL chạy trong Docker nên bạn khỏi phải cài trực tiếp".

Cài đặt: một lệnh

Cài aidev bằng một lệnh duy nhất:

curl -fsSL https://raw.githubusercontent.com/rgb-vgx/aidev/main/install.sh | sh

Nó tải bản phát hành đúng cho máy của bạn (Linux hoặc macOS, amd64 hoặc arm64), đối chiếu tập tin tải về với tập tin SHA256SUMS của bản phát hành (danh sách dấu vân tay: tập tin tải về không khớp sẽ bị từ chối, nên tập tin hỏng hoặc bị sửa đổi không bao giờ được cài), rồi đặt aidev vào ~/.local/bin. Cách này không cần Go.

Dấu hiệu thành công: nó in ra "Installed aidev v0.1.0 to ..." kèm các bước tiếp theo. Kiểm tra bằng:

aidev version
# muốn thấy: aidev v0.1.0 hoặc tương tự

"Nằm trên PATH" nghĩa là thế này: khi bạn gõ tên một chương trình, shell sẽ dò trong một danh sách thư mục gọi là PATH cho tới khi thấy chương trình khớp. Trình cài đặt đặt aidev vào ~/.local/bin, vốn đã nằm trong danh sách đó trên nhiều máy. Nếu ~/.local/bin chưa nằm trên PATH thì trình cài đặt sẽ in ra dòng export PATH để bạn thêm vào ~/.bashrc hoặc ~/.zshrc, nhờ đó gõ aidev ... ở thư mục nào cũng chạy, trong terminal mới nào cũng chạy, thay vì chỉ chạy được trong một thư mục.

Muốn cài một phiên bản cụ thể:

curl -fsSL https://raw.githubusercontent.com/rgb-vgx/aidev/main/install.sh | AIDEV_VERSION=v0.1.0 sh

Muốn cài sang chỗ khác:

curl -fsSL https://raw.githubusercontent.com/rgb-vgx/aidev/main/install.sh | AIDEV_INSTALL_DIR="$HOME/bin" sh

Từ mã nguồn, khi phát triển aidev

Nếu bạn muốn sửa chính aidev thì hãy biên dịch từ mã nguồn.

git clone https://github.com/rgb-vgx/aidev.git
cd aidev
make build
# tạo ra bin/aidev
./bin/aidev version
# muốn thấy: aidev <version>, ví dụ: aidev dev

Dấu hiệu thành công: quá trình biên dịch kết thúc không lỗi, và bin/aidev tồn tại. Nếu make build hỏng, hãy đọc thông báo lỗi, sửa đúng lỗi được nêu rồi chạy lại make build. Chạy lại thoải mái, không sao cả.

Đưa aidev lên PATH để terminal nào cũng tìm thấy nó:

make install
# chạy: go install ./cmd/aidev

Từ đây hướng dẫn sẽ viết aidev. Nếu bạn không cài theo cách đó thì chỗ nào thấy aidev hãy gõ ./bin/aidev.

Cơ sở dữ liệu và cấu hình: một lệnh, aidev setup

PostgreSQL là nơi aidev cất mọi thứ. Migration là tập tin SQL có đánh phiên bản, dùng để tạo hoặc sửa các bảng trong cơ sở dữ liệu. Chạy migration nghĩa là thực thi các tập tin đó theo thứ tự để cấu trúc cơ sở dữ liệu khớp với những gì chương trình mong đợi. Migration được nhúng sẵn trong chính chương trình aidev nên bạn không cần cài thêm công cụ migration nào.

Cách khuyên dùng là một lệnh duy nhất:

aidev setup

Lệnh này làm gì: nó khởi động PostgreSQL trong Docker, trong một container tên aidev-postgres, chỉ nghe trên chính máy này ở 127.0.0.1:5434. Nó ghi ~/.config/aidev/conf.json với database.url, một tập tin riêng tư không bao giờ bị ghi đè nếu đã tồn tại. Nó áp các migration. Rồi nó in ra dòng export và dòng thiết lập cho Claude Code để bạn thêm vào.

Chạy lại thoải mái, không sao cả, ví dụ sau khi khởi động lại máy: nó bật container lên nếu container đã dừng và giữ nguyên cấu hình của bạn.

Dấu hiệu thành công: lệnh kết thúc bằng dòng aidev is set up. kèm danh sách các bước tiếp theo.

Nếu công ty bạn lấy image Docker từ registry riêng thì hãy cho setup biết cần dùng image nào:

aidev setup --postgres-image registry.example.com/library/postgres:16-alpine

Nếu bạn đã có sẵn PostgreSQL thì trỏ setup tới đó. Nhớ đặt URL trong dấu nháy. Không cần Docker, nhưng cơ sở dữ liệu phải tồn tại sẵn:

aidev setup --database-url 'postgres://user:password@host:5432/aidev'

Nếu cổng 5434 trên máy bạn đã bị chiếm thì chọn cổng khác:

aidev setup --postgres-port 5440

Tiếp theo, trỏ aidev tới tập tin setup vừa ghi, như phần cấu hình dưới đây mô tả, rồi kiểm tra mọi thứ:

export AIDEV_CONFIG="$HOME/.config/aidev/conf.json"
# đặt dòng export đó vào shell profile (~/.bashrc, ~/.zshrc, hoặc tương đương)
aidev doctor

Dấu hiệu thành công: mọi dòng của aidev doctor đều báo ok, và mỗi lỗi đều nói rõ cách sửa.

Làm thủ công, từ repository

Nếu bạn làm việc trên chính aidev thì có thể làm các bước trên bằng tay ngay trong kho mã thay vì chạy aidev setup.

Khởi động PostgreSQL:

make db-up
# starts PostgreSQL and waits until it is healthy

Dấu hiệu thành công: lệnh chờ vài giây rồi báo container đã khỏe. Lệnh này khởi động một container PostgreSQL lắng nghe trên máy bạn ở 127.0.0.1:5434. Nếu cổng 5434 trên máy bạn cũng bị chiếm thì đổi cổng:

AIDEV_DB_PORT=5440 make db-up

Nếu make db-up hỏng thì thường do hai nguyên nhân: Docker chưa chạy (bật Docker lên rồi thử lại), hoặc cổng đã có chương trình khác dùng (chọn cổng khác như trên). Sửa rồi chạy lại lệnh, chạy lại thoải mái.

Tiếp theo, cấu hình kết nối rồi áp cấu trúc bảng. Chuỗi kết nối là một dòng chữ duy nhất cho chương trình biết cách tới cơ sở dữ liệu: đăng nhập tên gì, ở đâu, kèm tùy chọn gì. Bạn chỉ viết nó một lần vào conf.json của mình, ở khóa database.url, như phần cấu hình dưới đây mô tả:

cp conf/conf.example.json conf/conf.json
# rồi sửa database.url trong conf/conf.json nếu bạn đổi cổng
export AIDEV_CONFIG="$PWD/conf/conf.json"
# đặt dòng export đó vào shell profile (~/.bashrc, ~/.zshrc, hoặc tương đương)
aidev migrate
# want: "database is up to date (N migrations)" or a list of "applied ..." lines

Dòng đầu chép các thiết lập mẫu vào conf/conf.json. Nếu đổi cổng thì sửa database.url cho khớp. Dòng thứ hai cho aidev biết tập tin nào là conf.json của nó: AIDEV_CONFIG phải chứa đường dẫn tuyệt đối của tập tin, và đó là biến môi trường duy nhất aidev đọc để cấu hình. Dòng cuối áp các migration còn thiếu. aidev migrate có tính lũy đẳng, tức là chạy hai lần cũng không sao: lần thứ hai chẳng còn gì để làm và nó báo cơ sở dữ liệu đã cập nhật.

Nếu aidev migrate báo cấu hình không hợp lệ thì nó sẽ nêu tên thiết lập. Nếu không kết nối được thì kiểm tra xem make db-up còn chạy không, và cổng trong database.url có khớp với cổng cơ sở dữ liệu đang nghe không. Nếu bạn sửa một tập tin migration đã áp rồi thì bộ migrator sẽ từ chối khởi động và nói rõ: đừng bao giờ sửa migration đã áp, hãy thêm migration mới.

Cấu hình: tập tin conf.json quyết định

aidev đọc toàn bộ cấu hình từ một tập tin JSON duy nhất: conf.json mà AIDEV_CONFIG chỉ tới. AIDEV_CONFIG phải chứa đường dẫn tuyệt đối của tập tin, và đó là biến môi trường duy nhất aidev đọc để cấu hình. Mọi thứ nằm trong tập tin đó, và aidev kiểm tra toàn bộ ngay khi khởi động rồi báo hết mọi lỗi một lúc, thay vì chạy nửa chừng mới đổ vỡ.

Tạo tập tin một lần. Chép tập tin mẫu rồi trỏ aidev tới nó:

cp conf/conf.example.json conf/conf.json
# rồi sửa cho hợp: database.url, workspace_root, và những gì khác bạn cần
export AIDEV_CONFIG="$PWD/conf/conf.json"
# đặt dòng export đó vào shell profile (~/.bashrc, ~/.zshrc, hoặc tương đương)
aidev config
# in thiết lập đã nhận và cho biết đã dùng tập tin nào

aidev không đọc gì ngoài tập tin mà AIDEV_CONFIG chỉ tới, nên dòng export phải có mặt trong mọi terminal mới. Đặt dòng đó vào shell profile thì đây là việc làm một lần. Thiếu dòng export là lỗi: aidev config sẽ báo AIDEV_CONFIG is not set. Tập tin không đọc được là một lỗi khác có nêu đường dẫn: read config file <path>: .... Tập tin đã tồn tại mà không phân tích được, hoặc chứa khóa lạ, cũng là lỗi nêu rõ vấn đề, để thiết lập hỏng không bao giờ bị lặng lẽ bỏ qua.

Tập tin là JSON nên giá trị là chữ nguyên văn. Đổi cổng cơ sở dữ liệu thì sửa database.url; không có gì khác trong môi trường thắng được tập tin, nên những gì bạn đọc trong conf.json chính là những gì aidev dùng.

Danh sách đầy đủ kèm mọi giá trị mặc định nằm ở trang tra cứu. Muốn xem chính xác aidev đã nhận gì, với mật khẩu cơ sở dữ liệu đã che đi:

aidev config
aidev config --json

Dấu hiệu thành công: một bảng thiết lập với giá trị của bạn. Mật khẩu cơ sở dữ liệu hiện dạng đã che. aidev config cho biết đã dùng tập tin nào, hoặc báo không tìm thấy tập tin nào. Nếu aidev config báo lỗi thì nó liệt kê mọi vấn đề. Sửa hết rồi chạy lại. Cấu hình sai lộ mặt ở đây, ngay khi khởi động, chứ không đợi tới giữa task mới bung ra, đó chính là ý nghĩa của lệnh này.

Task đầu tiên: ví dụ làm thật trên kho mã dùng một lần

Giờ tới phần thật. Bạn sẽ tạo một kho mã thực hành nhỏ mà test của nó hỏng cho tới khi việc xong, rồi nhờ aidev làm. Kho mã dùng một lần là dự án nháp để xóa sau. Dùng nó để lần chạy đầu tiên tránh xa code thật.

Vì sao ví dụ có hình dạng này: task cần một lệnh verification hỏng trước khi làm và qua sau khi làm xong. Có vậy mới chứng minh được verification là bên quyết định. Một test đang hỏng là điểm xuất phát trung thực.

Bước 1. Tạo kho mã dùng một lần. Module ở đây chỉ là một dự án Go nhỏ. Các lệnh dưới tạo thư mục, khởi tạo kho git trong đó, rồi thêm một test chắc chắn hỏng vì hàm nó kiểm tra còn chưa tồn tại.

mkdir -p /tmp/aidev-demo
cd /tmp/aidev-demo
git init -b main
go mod init demo
cat > greet_test.go <<EOF
package main

import "testing"

func TestGreet(t *testing.T) {
    if Greet("Ada") != "Hello, Ada" {
        t.Fatalf("Greet returned the wrong string")
    }
}
EOF
go test ./...
# want: FAIL, something like: undefined: Greet
# that failure is the point: the test fails until the work is done

Nếu go test ./... ở đây lại qua thì có gì đó sai: có thể trong thư mục đã sẵn một tập tin greet.go. Xóa nó rồi chạy test lại. Bạn muốn một test đang hỏng.

Bước 2. Tạo task. Cờ --verify cho một lệnh verification. Muốn nhiều lệnh thì lặp lại cờ đó. Ít nhất một lệnh là bắt buộc: task mà aidev không kiểm được thì aidev không nhận.

cd /tmp/aidev-demo
aidev task create \
  --title "Add a Greet function" \
  --description "Create greet.go with Greet(name string) string returning Hello plus name" \
  --verify 'go test ./...' \
  --verify 'go vet ./...'
# want: created TASK-000001  Add a Greet function
#           run it with: aidev task run TASK-000001

Ý nghĩa các cờ: --title là một dòng ngắn nói cần làm gì. --description là hướng dẫn đầy đủ agent sẽ đọc. Mỗi --verify là một lệnh aidev tự chạy, không qua shell, để quyết định kết quả. Mã tham chiếu bạn nhận lại, kiểu TASK-000001, là cách gọi tên task từ nay về sau.

Nếu tạo thất bại với thông báo về verification thì bạn đã quên --verify. Nếu nó than đường dẫn không phải kho git thì kiểm tra xem bạn có đang ở trong /tmp/aidev-demo không và git status ở đó có chạy không.

Bước 3. Chạy nó:

aidev task run TASK-000001

Lệnh này mất bao lâu: tính bằng phút chứ không phải giây. Phần lớn thời gian chờ là model suy nghĩ, không phải aidev. Phần việc của riêng aidev trong một lần chạy, gồm tạo worktree, lấy diff, chạy verification và mọi lần ghi cơ sở dữ liệu, được đo chỉ khoảng 0,2 giây, trong khi agent tốn từ 9 tới 656 giây. Model mặc định là bản nhanh và ổn định, nhưng độ trễ của bản miễn phí thất thường. Nếu mất mười phút thì đó là do model, không phải lỗi. Trong lúc chạy, bạn có thể mở terminal khác xem nhật ký event như trang gỡ lỗi mô tả.

Nếu lệnh bị ngắt bằng Ctrl-C thì task bị hủy và worktree được giữ lại. Như vậy là an toàn. Xem phần khôi phục để biết bước tiếp theo.

Đọc kết quả

Khi chạy xong, lệnh sẽ báo kết quả. Thành công trông thế này:

TASK-000001 succeeded: 2/2 verification steps passed, work committed on aidev/TASK-000001

agent (opencode)
  outcome       SUCCEEDED
  changed files 1
  took          10m56s

verification (run by aidev)
  PASSED    go test ./...
  PASSED    go vet ./...

Đọc nó làm hai nửa. Nửa agent nói agent đã làm gì và nó nói gì. Nửa verification nói aidev tự xác minh được gì. Chỉ nửa thứ hai quyết định. aidev task run thoát với mã 0 khi thành công và mã khác 0 khi task không thành công, nên aidev task run TASK-000001 && ./deploy.sh đúng như người dùng shell mong đợi: lệnh thứ hai chỉ chạy khi task đã thành công.

Thất bại trông thế này:

TASK-000002 FAILED (VERIFICATION): verification did not pass: 0/1 steps passed

agent (opencode)
  outcome       SUCCEEDED
  changed files 0
  says          Done! I implemented the function and all tests pass.

verification (run by aidev)
  FAILED    go test ./...  (exit 1)

the work was kept for inspection

Để ý nửa agent: nó nói thành công. Để ý nửa verification: bước kiểm tra hỏng. Task là FAILED, vì chỉ verification quyết định. Đây là quy tắc duy nhất trong thực tế. Lời agent được ghi lại vì giúp chẩn đoán, chứ không bao giờ là bằng chứng.

Hai lệnh cho bạn xem thêm bất cứ khi nào cần:

aidev task result TASK-000001
aidev task result TASK-000001 --logs

Lệnh đầu cho kết quả của attempt mới nhất: trạng thái, thời gian, kết quả verification từng bước, và công việc đang ở đâu. Lệnh thứ hai thêm bản ghi của agent, diff và toàn bộ output verification. Output của bước hỏng luôn được kèm theo ngay cả khi không có --logs, cắt lấy 2000 byte cuối, vì đó là thứ ai cũng cần đầu tiên.

Công việc nằm ở đâu, và cách xem lại nhánh bằng git

Khi thành công, aidev commit phần việc của agent lên nhánh (branch) riêng của task rồi xóa worktree. Nhánh đặt tên theo mã task, ví dụ aidev/TASK-000001. Không có gì được merge vào nhánh của bạn. Không bao giờ có commit nào lên nhánh bạn đang làm. Bản checkout của bạn vẫn sạch.

Xem lại kết quả bằng lệnh git thường. git log liệt kê commit. git diff cho thấy hai nhánh khác nhau chỗ nào.

cd /tmp/aidev-demo
git log --oneline aidev/TASK-000001
git diff main..aidev/TASK-000001
go clean -testcache && go test ./...
# run the test yourself on your own checkout of the branch:
# it should pass, because verification already passed in the worktree

Khi thất bại, worktree được giữ nguyên như agent để lại, nằm dưới workspace_root, và ghi nhận là RETAINED. Đó là chủ ý: công việc dở dang thường là thứ hữu ích nhất của một lần hỏng. Tìm nó bằng aidev worktree list, xem xét, và chỉ xóa khi đã xong. Trang gỡ lỗi hướng dẫn từng bước việc đó.

Làm xong demo thì xóa thư mục dùng một lần. Rồi đọc tiếp trang đầu hướng dẫn, trang gỡ lỗi cho mọi thứ có thể hỏng, và trang tra cứu cho danh sách đầy đủ cờ và biến.

cd /tmp
rm -rf /tmp/aidev-demo
aidev task list
# your demo task is still in PostgreSQL: the record outlives the directory

Quay lại vào ngày mai: nếu bạn đã đóng terminal thì không cần cài đặt lại gì cả ngoài dòng export trong shell profile. Hãy chắc PostgreSQL đang chạy bằng make db-up, rồi cứ gõ aidev. Cấu hình của bạn đã nằm sẵn trong conf.json mà AIDEV_CONFIG chỉ tới, dòng export trong shell profile đưa nó vào mọi terminal mới, và nhờ make install nên lệnh aidev vẫn tìm thấy. Muốn chắc thì chạy aidev config để xem trước khi chạy task.

Kết nối Claude Code: giao việc từ bất kỳ kho mã nào

Từ đầu trang tới giờ bạn dùng aidev ở terminal. Nhưng aidev được làm ra để Claude Code điều khiển: Claude Code quyết định cần làm gì và viết task, còn aidev cô lập task, chạy agent, rồi tự kiểm tra kết quả. Hai bên nói chuyện qua MCP (Model Context Protocol), một cách chuẩn để Claude Code gọi công cụ nằm trong chương trình khác. Bạn chỉ đăng ký aidev một lần, sau đó mọi kho mã trên máy đều dùng được.

make install
# puts aidev in $(go env GOPATH)/bin, a path that does not move

claude mcp add --scope user -e AIDEV_CONFIG=/abs/path/conf.json aidev -- "$(go env GOPATH)/bin/aidev" mcp
# registers aidev for every project on this machine; use the absolute path
# of the same conf.json that aidev config reports

Hãy dùng --scope user. Nếu bỏ cờ này, Claude Code dùng phạm vi local, tức là gắn việc đăng ký vào đúng thư mục bạn đứng khi gõ lệnh. Khi đó aidev chạy được ở kho mã đó và không tồn tại ở bất kỳ kho nào khác. Không có thông báo lỗi nào cả: công cụ chỉ đơn giản là không có. Đoạn này viết ra chính là để bạn tránh lỗi đó.

Không có mật khẩu hay chuỗi kết nối nào nằm trong phần đăng ký ngoài tập tin mà nó chỉ tới. aidev đọc conf.json mà AIDEV_CONFIG chỉ tới, cũng là tập tin mà các lệnh terminal dùng, nên aidev config cho bạn thấy đúng những gì máy chủ MCP sẽ thấy.

Kiểm tra việc đăng ký từ một thư mục không phải kho mã aidev, vì phạm vi sai chỉ lộ ra ở đó:

cd /tmp
claude mcp get aidev

Dấu hiệu đúng. Dòng quan trọng là dòng phạm vi (scope):

aidev:
  Scope: User config (available in all your projects)
  Status: ✔ Connected
  Type: stdio
  Command: /home/you/go/bin/aidev
  Args: mcp

Nếu dòng scope ghi bất cứ thứ gì khác User config, hãy gỡ đăng ký bằng đúng lệnh in ở dòng cuối của output đó, rồi chạy lại lệnh claude mcp add --scope user. Nếu trạng thái không phải Connected thì aidev không khởi động được: chạy aidev config ở terminal, lệnh này sẽ báo lỗi với đúng lý do mà máy chủ MCP gặp.

Sau khi đăng ký, hãy mở một phiên Claude Code mới. Phiên đã mở từ trước không nhận máy chủ được thêm vào sau.

Dùng ở kho mã khác thì không cần cài gì thêm cho từng kho. Mở Claude Code trong kho mã đó, ví dụ trong VS Code, rồi yêu cầu bằng lời thường, kèm lệnh kiểm tra chứng minh việc đã xong: "Dùng aidev thêm hàm farewell vào greet.py, kiểm tra bằng python3 -m pytest -q." Claude Code sẽ gọi aidev_create_task và aidev_run_task, rồi đọc aidev_get_task_result. Trường quyết định là succeeded, chỉ bằng true khi chính verification của aidev đã đạt. Điều kiện duy nhất: kho mã phải là kho git, và PostgreSQL phải đang chạy (make db-up trong thư mục aidev).

Một điều hay làm người mới bất ngờ khi dùng với kho mã thật: worktree là một bản checkout sạch, nên chỉ chứa các file git đang theo dõi. Thứ gì cài bên ngoài git thì không có ở đó. go test chạy được vì bộ nhớ đệm module của Go dùng chung, nhưng dự án Python hay JavaScript cần công cụ test đã cài sẵn trên máy, hoặc một bước verification cài nó trước. Trang tra cứu liệt kê mọi công cụ và đầu vào của chúng.
